## 問題

「この件に関する裁判例を調べて」「民法第555条の内容を教えて」で正しい段落が返らなかった。原因は5つある。

1. **1ファイル1段落しか LLM に返らなかった。** `SearchBackend::search` はパスでグループ化して最良ユニットだけを返していた。民法は全体が1ファイルなので、何条一致しても1条しか渡らない。長い契約書・議事録でも同じ。設定の「検索件数」は段落数ではなくファイル数だった。
2. **複合語が OR に崩れていた。** 索引トークナイザは `Mode::Decompose` なので `裁判例` は `裁判` + `例` として索引される。クエリ側も同じく分解され、各トークンが `Occur::Should` で積まれていたため、`例` にだけ当たる文書が候補に入った。
3. **自然文クエリが実質 OR だった。** 区切り文字がないので文全体が1 include になり、全トークンが Should、`min_overlap = 1` で1語一致でも通過した。
4. **スコアが非単調だった。** `combined = overlap * 10 * compact + score` は、1語一致（`compact = 1.0`）が10点を確実に取る一方、3語一致はスパンが広いと10点未満になり負けた。
5. **`read_unit` が呼べなかった。** `format_sources` が `paragraph_id` を出さないので、切り詰められた段落の続きを読む手段がなかった。

---

## 方針

### 再索引を避ける

`INDEX_SCHEMA_VERSION` を上げると起動時に索引を全破棄して再構築が走る。スキーマには一切触らず、**クエリ構築・返却粒度・rescore** だけで改善した。

`unit_label`（段落見出し）はトークナイズしていないが `stored` なので、検索時に文字列として突き合わせるだけでピンポイント性が上がる。同じ理由で、条文境界でのユニット分割ではなく `read_unit` の前後読みで長条文に対応した。

### ポップアップと LLM を分ける

検索バックエンドは2つの用途で共用されている。

| 用途 | クエリ | 欲しいもの |
|------|--------|------------|
| ポップアップ | ユーザーが選択した文 | 再現率。1語一致でも有用 |
| チャットツール | 質問 | 適合率。段落単位 |

緩さは既存テスト（`sentence_query_hits_doc_with_only_noun`）で意図的に守られているので、**返却粒度と指示語除去は `SearchOpts` で LLM 経路のみ**にした。純粋なバグ（スコア非単調性、title のフィールド長インフレ）は全経路に適用した。

AND 化だけは条件付きで両経路に効かせる。**語を空白で区切るのは意図的な行為**で、ユーザーは「この語が入っている文書」を列挙したのだから、大半の一致を要求するのが指示通りである。選択文には区切りがないので1 include のまま緩い経路を通る。

```rust
let require_most = opts.precision || parsed.includes.len() >= 2;
```

指示語除去は空白区切りには適用しない。質問文の定型語を落とすのは、チャットが疑問文を投げてくるからで、ユーザーが打った語は字面どおりの要求である（`場合` と打ったなら `場合` を探している）。

```rust
pub struct SearchOpts {
    /// 検索単位の一定割合の一致を要求し、質問文の定型語を落とす。
    pub precision: bool,
    /// Some(n) でユニット単位に返す（1ファイルあたり最大 n）。None は現行のファイル単位集約。
    pub per_file_units: Option<usize>,
}
```

リモート／ハイブリッドのファイル検索では `SearchOpts` を落としている。段落単位のローカルヒットとファイル単位のリモートヒットが混ざると、統合後の順位が意味を失うため。

## 検索単位

クエリを**検索単位**に分ける。1単位 = 1 Should 節。

| クエリ | 検索単位 |
|--------|----------|
| `この件に関する裁判例を調べて` | `[裁判例]` |
| `業務委託契約の解除` | `[業務委託契約]`, `[解除]` |
| `民法第555条の内容を教えて` | `[民法]` + 条文引用節（Must） |

処理は3段。

1. **複合語検出**（`MorphAnalyzer::query_units`）。連続する `名詞`（`非自立`・`代名詞` を除く）を1単位にまとめる。`接頭詞` は後続名詞に吸収させる（`第` + `555` + `条` → `第555条`）。単独の `第` は全法令に当たるので単位にしない。
2. **質問表現の除去**（`is_query_intent_term`、`precision` 時のみ）。`内容` `件` `場合` `教え` `調べ` などを落とす。**単独単位にだけ**適用するので `本件` `因果関係` の `件` `関係` は残る。他に単位が残らない場合は落とさない。
3. **索引トークン化**。各単位を `tokenize_ja` に通し、1トークンなら `TermQuery`、複数なら `PhraseQuery`。索引トークナイザ自身の出力を使うので、転置索引に存在しない Term を作ることがない。

条文引用がある include は、`legal_cite_group` が既にその文字を要求するので `mask_legal_refs` で伏せる。伏せないと Should の分母を二重計上する。

## 段階的 AND 化

`BooleanQuery::with_minimum_required_clauses` で「検索単位のうち何個一致すべきか」を課す。厳しい段から順に試し、結果が残った段を採用する。

| 段 | `require_most` | 空白なしの選択文 |
|----|----------------|------------------|
| 1 | 単位数の 70% | 1 |
| 2 | 単位数の 50% | — |
| 3 | 1 | — |
| 4 | 条文引用を Should に落とす | — |
| 5 | 複合語を単語に分解 | — |

**Must 節があるときは最低数を 0 にする。** 条文引用や引用符付きフレーズがクエリの厳しい部分なので、残りの語まで要求すると `民法 第555条` が0件になる（法令ファイルの各条文は法令名を繰り返さない）。tantivy は最低数が Should 節数を超えると `EmptyScorer` を返し、Should が0個のときも同じなので、`0..=Should節数` にクランプしている。

同じクエリを再実行しないよう、`(最低数, 引用必須, 分解)` が前段と同じ段はスキップする。

rescore 側の `min_overlap` は、その段が実際に要求した割合から導く。割合0のときは従来の規則（POS フィルタ有効なら1、無効なら半数）をそのまま使う。

**段の判定は rescore 後の残存件数で行う。** `min_overlap` は `find_occurrences` の文字単位一致に依存するが、これは大文字小文字を区別する一方、索引側は区別しない。`契約書 PDF` は索引では `pdf` に当たるのに近接計算では当たらないので、リトリーバルのヒット数だけで段を決めると、上位段が取得した文書を後段フィルタが全部落として0件になる。段を残存件数で判定すれば、最終段が従来のクエリそのものなので、**厳しい段は結果を絞るだけで、従来ヒットしていたものを0件にはできない**。

## スコア

```rust
let coverage = overlap as f32 / proximity_tokens.len() as f32; // 0..1
let combined = score * (1.0 + 1.5 * coverage + 1.0 * coverage * compact + 0.6 * label);
```

BM25 への**乗算**にしてスケール非依存にし、`coverage` を通すことで**一致単位が増えてスコアが下がらない**ことを保証した。`compact`（近接度）は既に広く一致しているヒットを後押しするだけで、単独では順位を決めない。

近接計算に渡すトークンは複合語のまま。部分文字列マッチなので、`裁判例` を `裁判` と `例` に割ると1一致を2一致と数えてスパン計測も壊れる。

### title の減衰

`title` はファイル名で数トークンしかないため、BM25 のフィールド長正規化で1語一致でも過大評価される。ただし裁判例のファイル名は裁判所・事件番号・日付を持つ実質メタデータなので潰せない。`BoostQuery` で 0.6 に減衰させ、「ファイル名だけ一致」が「本文で複数一致」に勝たない程度に留めた。

### 見出し一致ボーナス

`unit_label` は段落先頭の `第N条…` か先頭36文字なので、実質的に見出しとして機能する（`第3 争点`、`1 事実の概要`）。

- 見出しが検索単位で**始まる** → 満点（1.0）
- 見出しが検索単位を**含む** → 半分（0.5）

条文そのもののラベルは `第五百五十五条…` で始まる。それを論評する解説文のラベルは `解説として、第五百五十五条の…` で始まるので、段階を付けることで条文本体が上に来る。

## 返却粒度

`per_file_units = Some(3)` のとき、パスごとに `dedupe_path_units` 後の上位3ユニットを平坦に返し、全体で `limit` 件で打ち切る。返し切れなかった一致段落があるファイルは、ツール応答の末尾に件数を添えてモデルに伝える。

メールは1通=1ユニットなので `per_file_units` を無効化している（長いメールが複製されるだけになる）。

---

## ツール I/O

- `TOOL_BODY_CAP = 1200` は維持。1ユニットは最大1000文字なので通常の条文・段落は丸ごと入る。切り詰めが起きたときだけ末尾に ` […]` を付け、ツール説明でそのマーカーを指す。
- `format_sources` は段落粒度の出典に `(paragraph_id: ...)` を出す。これがないと `read_unit` を呼べず、切り詰められた出典が行き止まりになる。ファイル全体粒度の出典には出さない（再読すべき単一段落がない）。
- `read_unit` は cap を 6000 文字に上げ、`with_neighbors` で前後ユニットも読める。段落IDは `<path>#<unit_id>` で、Windows パスは `#` を含みうるので**最後の** `#` で分割する。メールは隣が無関係な別メールなので前後読みを無効化。
- 既読ヒットには先頭120文字を添える。文脈組み立てで元の本文が退避されている場合、タイトルだけではモデルに何も残らない。

### ツール予算

`assemble_turns` は**ツール実行前に**文脈量を決めるので、後から積まれるツール結果は純粋な超過分になる。`llm_max_context_chars` の 1/4 を予約枠とし、超える分は切って「省略」と伝え、枠を使い切ったらラウンドを打ち切って手持ちの出典で答えさせる。

## フォルダスコープ

`llm_threads.path_prefix` 列は既にあったが**書き込み関数も参照箇所もなかった**。マイグレーションなしで有効化した。複数フォルダは同じ列に改行区切りで入れる（パスに改行は含まれない）。

- `Db::set_llm_thread_scope` と Tauri コマンド `llm_set_thread_scope`（`pathPrefixes: string[]`。空配列で解除。親が選ばれていれば子は落とす。上限 8）
- `ChatScopePicker`（`list_search_scopes` と `mail_list_selected_folder_names` を再利用、`mailfolder:` も選べる。直近・複数選択・外側クリック／Esc／×）
- `execute_tool` に渡し、`search_index` に強制適用。複数時はフォルダごとに検索してスコア順にマージ

**スレッドスコープは外枠として固定する。** モデルが `path_prefix` を渡してきた場合、どれかのスコープ配下（より狭い絞り込み）と確認できたときだけ採用し、外にあるものは破棄してスレッド側の全フォルダを使う。従えば、ユーザーが除外したフォルダを黙って検索することになる。

スコープ設定時はシステム文に1行注入する。これを省くとモデルが0件の理由を誤解し、皮相な再検索を繰り返す。0件メッセージにもスコープ名を含める。

- 条文境界でのユニット分割とラベル継承（今回は `read_unit` の前後読みで代替）
