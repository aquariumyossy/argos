# 要件事実ダイアグラム — 描画ルール

最終更新: 2026-08-16  
状態: チャットの Mermaid 描画は入っている。**参照データの選び方・渡し方は未整備**で、図の質は添付出典に強く依存する。

実装: `src/features/chat/AssistantBody.tsx`、`mermaidSanitize.ts`、`assistantMd.ts`、`Chat.tsx`（テンプレ）、`src-tauri/src/llm/mod.rs`（図を頼まれた回だけヒント）

## 役割の分担

アプリは図を「発明」しない。モデルが Mermaid を書き、アプリはパースして描く。

| 層 | やること | やらないこと |
|----|----------|--------------|
| 出典 | 訴状・答弁・契約など、図の根拠になる本文を `[n]` で渡す | 要件事実の構造をアプリが抽出する |
| モデル | `flowchart LR` をフェンス1本で書く。出典にない事実はノードにしない | ASCII の枠線図、生 HTML |
| アプリ | フェンス検出、ソース補正、SVG 描画、図／ソース切替 | 保存済みメッセージの Mermaid 本文を書き換える |

補正は描画直前だけ。会話に保存されるソースはそのまま。

## アプリ側の描画ルール（実装済み）

### レイアウト

- 向きは **左→右**（`flowchart LR` / `graph LR`）。
- 左に請求原因、その右に抗弁、さらに右に対応する再抗弁。
- 描画時、`flowchart` / `graph` の `TB` / `TD` / `BT` は `LR` に直す（既存回答の縦図も開き直しで横になる）。
- `sequenceDiagram` などフローチャート以外は向きを変えない。
- 図が広いときは箱を縮めず、ビューを横スクロールする（`max-width: 100%` で潰さない）。

### ノード

- **請求原因は1ノード。** 主要事実が複数でも箱を分けない。番号や短い句を同じラベルに書く。
- 描画時、ラベルが「請求原因」で始まる箱が2つ以上あれば1つにまとめる（間の辺は捨て、残りの辺は残した ID に付け替える）。
- **抗弁は種類ごと**にノードを分ける。その右に、その抗弁への再抗弁を置く。
- ラベルは短く。種別（請求原因 / 抗弁 / 再抗弁）と要点と出典番号だけ。
- 各ノードに添付出典の `[n]`。出典にない事実はノードにしない（モデルへの指示。アプリは事実の真偽を見ない）。

### Mermaid の書き方（モデルへ）

- フェンスは言語タグ `mermaid`。1回答に図はフェンス1本を基本とする。
- ラベルは引用符で囲む: `Kg["請求原因：契約成立 [2]"]`。
- 矢印は `-->` または `-.->`。矢印記号の途中に空白を入れない（`-.- >` は不正）。
- 枠線文字（`+--+` や `v`）の ASCII 図は使わない。

「要件事実」バッジの文面と、ユーザーが「ダイアグラムを作って」などと書いた回だけシステムへ足す短いヒントが、上を指示する。**通常の回答のシステムプロンプトには Mermaid の書き方を常時載せない**（ローカルモデルが毎回答で図を出しやすいため）。

### パースを通すための補正（`sanitizeMermaidSource`）

モデル出力を描画する直前にだけかける。

1. 壊れた点線矢印（`-.- >` など）を `-.->` にする。
2. `Kg[… [13][2]]` のようにラベル内の `[n]` が箱の閉じ括弧と衝突しているとき、ラベル全体を引用符で囲む。
3. フローチャートを横向きにする。
4. 「請求原因」ラベルの箱を1つにまとめる。

言語タグが空でも、本文先頭が `flowchart` / `graph` なら Mermaid として描く。パースに失敗したら「ソース」を出し、エラー文を付ける。

### 見た目

- 図内の文字サイズはチャット本文（設定のフォントサイズ）を超えない。本文は `.chat` の `fontSize`、図は描画時にそれを渡し、CSS でも `1em` を上限にする。
- `securityLevel: "strict"`。LLM の生 HTML は図に出さない（`htmlLabels: false`）。
- ノード内の `[n]` は SVG 上のボタンにはしない（本文側の `[n]` だけがプレビューを開く）。

## 参照データ側（未着手・図が崩れる主因）

描画ルールを守っても、渡した本文が薄い・断片的だと図は分割されるか、ASCII に逃げるか、出典のない箱が増える。いまの添付は検索ヒットの段落（`grain=unit`）が中心で、要件事実図が必要とする「請求の骨格が通読できる塊」になっていないことが多い。

観測されたずれ:

- **請求原因が複数箱になる。** 契約成立と代金未払が別段落・別 `[n]` としてしか無いと、モデルは箱を分ける。アプリは「請求原因」で始まるラベルだけ後から結合する。ラベルが「主要事実」だけだと結合しない。
- **抗弁の抜け・過剰。** 答弁書や契約の失権条項が添付に無いと出ない。逆に、関係の薄いヒット段落があると抗弁が増える。
- **`[n]` がノードに載らない / 衝突する。** 出典集合と図の番号がずれる。ラベル内の `[n]` は Mermaid の文法を壊しやすい（補正済み）。
- **訴状の「請求の原因」節が一塊で渡らない。** 段落粒度だと要件の列挙が途中で切れる。ファイル粒度（`grain=file`）は長い文書で予算を食う。
- **図用にツール検索しても、返るのは適合した段落であり、要件事実の階層ではない。** `search_index` / `read_unit` は条文・フレーズ向け。請求原因→抗弁→再抗弁の対応表は作らない。

手を入れるなら（未スケジュール、索引スキーマは触らない）:

1. 要件事実図を頼まれたとき、訴状・答弁など **主張書面をファイル粒度または連続ユニットで優先して載せる**（ヒット1段落だけにしない）。
2. 同じパスの前後段落を `read_unit` で足す予算を、図の回だけ厚くする。
3. ノードに載せる `[n]` は、そのターンで実際にコンテキストへ入った出典に限る（描画側で番号を足さない）。
4. モデルに「添付の見出し・項番号をノード ID にしない。事実の種別で箱を分ける」と明示する（テンプレ済み。データが揃って初めて効く）。

Tantivy スキーマと `files` 表は触らない。出典はこれまでどおり `llm_thread_sources`。メッセージ本文に出典を埋め込まない。

## 触らないこと

- 会話ログ内の Mermaid ソースの永続書き換え
- 図の SVG / PNG 書き出し（フェーズ5）
- アプリが要件事実をルールベースで抽出して図を組み立てること
- 毎ターンのシステムプロンプトへの Mermaid 手順の常時掲載
