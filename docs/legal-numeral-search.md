# 条文番号の表記ゆれ検索

最終更新: 2026-08-15  
状態: **実装済み**（スキーマ変更なし、再索引なし）。

関連コード:

- `src-tauri/src/search/legal_ref.rs` — 条文番号のパースと整形
- `src-tauri/src/search/tantivy_backend.rs` — 検索経路への接続

---

## 問題

法令・判例の本文は位取り漢字が多い。索引本文には別名を載せていないので、アラビア数字のクエリはそのままでは当たらない。

| クエリ | 本文の典型 | 以前の結果 |
|--------|------------|------------|
| `第555条` / `民法第555条` | `第五百五十五条` | 当たらない |
| `第509条` | `第五〇九条`（古い判例の〇埋め） | 当たらない |

Lindera はだいたい次のように切る。`555` という数字トークンは位取り漢字の本文に無い。

| 原文 | 典型的なトークン |
|------|------------------|
| 第五百五十五条 | `第` `五百` `五十五` `条` |
| 第555条 | `第` `555` `条` |
| 第五五五条 | `第` `五` `五` `五` `条` |

---

## 解き方

索引は原文のまま。**retrieval と rescore で別々の道具を使う**。

| 段 | 対象 | 手段 |
|----|------|------|
| retrieval | 転置索引（クエリ時に正規化できない） | 別名を隣接フレーズにして OR |
| rescore | 保存本文（クエリ時に触れる） | クエリと本文の**両側**をアラビア正規形へ |
| ハイライト | 保存本文 | 別名を全部渡し、本文にある表記だけ残す |

`body` / `title` は元から `IndexRecordOption::WithFreqsAndPositions` なので PhraseQuery が使える。スキーマは無変更（`INDEX_SCHEMA_VERSION = 5` / `MAIL_INDEX_SCHEMA_VERSION = 2` 据え置き）。

### 1. retrieval — 別名フレーズの OR を Must

`legal_cite_group`（`tantivy_backend.rs`）がクエリ中の条文参照から別名を作り、索引と同じ `lang_ja` で切って PhraseQuery を OR する。

```
第555条 → (第555条 | 第５５５条 | 第五五五条 | 第五百五十五条)
```

- **単語 OR はしない**。`五` や `百` を単独で OR すると民法のほぼ全件が候補になり、555 条が埋もれる
- 本命は `第` + 数字トークン列 + `条` の隣接。`第千五百五十五条` は `第` と `五百` が隣り合わないのでフレーズとしては当たらない
- 1 トークンにしかならない別名は捨てる（`phrase_in_title_or_body` が TermQuery OR に落ちるため、頻出語 1 語が Must に化けるのを防ぐ）
- 引用句 `"第555条"` は展開しない。引用は完全一致の意思表示

Occur は **Must**。`民法第555条の条文を示して` が民法の全チャンクに埋もれないようにする。0 件だった場合だけ Should に緩めて再検索する（`cite_must_empty -> cite_should`）。既存の `loose_retrieval` フォールバックの手前の段。

### 2. rescore — 両側をアラビア正規形に畳む（ここが要）

**クエリ展開だけでは足りない。** `search_scored` の後段は保存本文への部分文字列一致で `overlap` を数え、`min_overlap` 未満を捨てる:

```rust
let (overlap, span) = proximity_span(&prox_hay, &proximity_tokens);
if min_overlap > 0 && overlap < min_overlap { continue; }
```

`第555条` の近接トークンは POS フィルタ後ほぼ `555` だけ。`第五百五十五条` の文書は Tantivy が拾っても**ここで必ず落ちる**。

そこでクエリに条文参照があるときは `normalize_legal_refs` をクエリと候補本文の両方に適用する（`cite_norm` フラグ）。`第五百五十五条` も `第五〇九条` も `第555条` に畳まれるので、どの表記で入力しても近接判定が成立する。

**片側だけでは駄目**。本文だけ正規化すると `第五百五十五条` と入力したときに近接トークン `五百` / `五十五` が正規化後の本文から消えて逆に落ちる。

`content_tokens`（retrieval 用のトークン）は正規化しない。`第五百五十五条` と入力したときの既存の当たり方を壊さないため。

除外フレーズの判定は原文のまま。`-第五百五十五条` はその表記を指す。

### 3. ハイライトとスニペット

`highlight_terms_for` が別名を全部積む。`hit_from_doc` が `haystack.contains(t)` で絞るので、実際に本文にある表記だけがチップに残る。`make_snippet` は候補を長い順に見るので、7 文字の `第五百五十五条` が `民法` より優先されスニペットが正しい位置に寄る。オフセット計算は不要。

### 認識範囲

`find_legal_refs` は**数字の直後に単位（条/項/号/編/章/節/款/目）を要求する**。

- 展開する: `第555条` `555条` `民法555条` `第五百五十五条の二` `第10項`
- 展開しない: 裸の `555`、`2026年5月15日`、`555円`

裸の 3〜4 桁も条文とみなす案はあったが、年号・金額・電話番号を巻き込むので採らなかった。

## やってうまくいかなかったこと（再導入しないこと）

### 索引に別名を載せる＋スキーマバージョン上げ

本文の第二値として `第555条 第五五五条 第五百五十五条` を `add_text` した。フィールド定義は変えていないのに全文再索引が必要になり、コストが見合わない。クエリ側で解けるので不要。

### クエリ文字列全体を漢数字に書き換える

`民法第555条の条文を示して` 全体を位取りにすると、本文にその語順が無い。展開するのは短い引用だけにする必要がある。

### `五` や `百` を単語 OR する

民法のほぼ全件が候補になり、555 条が埋もれる。
